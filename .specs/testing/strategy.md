## Unit Testing

**Framework:** bun:test

**What to test:**
- Cron expression validation (valid/invalid expressions)
- Next-execution calculation (including edge cases: DST, midnight, end-of-month)
- Task CRUD operations (add, remove, update, list, pause/resume)
- CLI argument parsing (valid flags, missing args, unknown flags)
- History formatting and filtering

**What NOT to unit test:**
- Actual crontab writes (use integration tests with mock)
- Actual shell script execution (use integration tests)
- `cc-hub` calls (mock in integration tests)

**File convention:**
- Test file lives next to source file: `tasks.ts` → `tasks.test.ts`
- Test names reference the AC: `"AC-001: creates task entry in tasks.json"`

**Example:**

```typescript
// src/cron.test.ts
import { test, expect } from "bun:test";
import { validateCronExpression, getNextExecution } from "./cron";

test("AC-003: rejects invalid cron expression", () => {
  expect(() => validateCronExpression("not a cron")).toThrow();
});

test("AC-004: calculates next execution for daily at midnight", () => {
  const next = getNextExecution("0 0 * * *");
  expect(next).toBeInstanceOf(Date);
  expect(next.getHours()).toBe(0);
  expect(next.getMinutes()).toBe(0);
});
```

## Integration Testing

**Framework:** bun:test + Bun.$

**What to test:**
- Wrapper script generation and execution (exit code propagation)
- Crontab entry creation and removal (using a test crontab file, not system crontab)
- History recording after script execution
- Telegram notification trigger on failure (mock `cc-hub` with a spy script)

**Test isolation:**
- Use a temp directory for `tasks.json` and wrapper scripts
- Never touch the real system crontab in tests
- Mock `cc-hub` by prepending a fake `cc-hub` to `PATH`

---

## What This Project Does NOT Test

- **No E2E tests** — no UI, no browser, no multi-service flows
- **No visual tests** — no screens to capture
- **No load/performance tests** — single-user tool, performance is not a concern
- **No API contract tests** — no API
